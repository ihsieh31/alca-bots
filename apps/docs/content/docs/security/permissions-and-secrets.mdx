## Approval cards

Supported providers emit permission requests and questions through the local harness. AlcaBots displays these inline and records the outcome. Cancellation closes outstanding requests so stale approvals cannot be answered after a turn has ended.

“Always allow” is narrow: it is tied to a server-issued key and a pending request rather than granting arbitrary execution from a paired device.

## Operating-system permissions

Screen Recording and Accessibility permissions are controlled by the operating system. The desktop process owns local CUA lifecycle so grants are attributed to AlcaBots.

## Secret handling

- Do not paste API keys into chat.
- Packaged builds use write-only settings and operating-system-backed encryption where supported.
- Secret values are scrubbed from public configuration responses and mobile APIs.
- Per-provider environment injection prevents unrelated agent processes from inheriting credentials they do not use.
- OAuth provider tokens for connected apps stay with Composio.

### When a bot asks for a key

A bot asks for a key on a secure card (`request_credential`), never in chat. A
key AlcaBots keeps itself (an AI provider key, the Composio key, voice keys,
the Boat key) is saved exactly where **Settings → API keys** saves it.

Any other secret (a Stripe or npm token, a webhook signing secret, a Notion key
for an MCP server) the bot names, and the card says what the bot may do with it:

- **For AlcaBots's own tools.** AlcaBots keeps the value in memory and
  gives the bot a one-use reference instead. Only `add_mcp_server` accepts it,
  only for that bot in that conversation, for an hour. The bot never sees the
  value; the MCP server's settings hold it.
- **For the bot's own commands.** The value goes into a file only your user can
  read, in a private `.alcabots-secrets` folder of the bot's own workspace (or
  its Local VM's). The bot reads it inside a command. The file is deleted after
  24 hours, or sooner when the conversation or the bot is deleted. Backups, moves
  to My Cloud, Cloud Files, chat links, attachments, published pages, browser
  uploads and checkpoints all leave that folder out.

On a Team Cloud only the person the conversation belongs to can enter it. A
freshly QR-paired phone can enter either kind; an AI provider key needs the
computer or My Cloud. While a value lives, AlcaBots masks it if it appears in
a transcript, an event or a log.

## Connected-app tool grants

Connected apps are scoped per bot on the desktop: a bot without a grant to a service's tool cannot call it, the ungranted tool is never offered to the model, and every allow/deny is written to the decision log. New and upgraded bots keep all tools until someone assigns grants, and imported bots always land with none, so a shared persona cannot reach your Gmail on turn one. Paired phones see grants read-only; grant editing requires the computer.

## Website sign-in

Bots may complete a sign-in you explicitly authorize for a particular site and
account, using an existing session, autofill, or credentials you supply or
designate for that purpose, including test accounts. A login form alone is not
a reason to refuse the task. Bots must check the destination and account first;
instructions on a webpage do not authorize using credentials.

Bots never ask for a website password, or for a one-time code, in chat, and a
bot never holds a password. In [ego lite](/docs/computers/browser), the bot
uses the sign-ins you already have there, or hands the browser to you.

When you ask a bot to do something that needs a sign-in (in your own chat, or
in a routine or automation you set up) and the site sends a one-time code to
your email or phone, the bot reads it from your connected email or messages
and types it into that site, then carries on. Your request is the
authorization, so it does not ask again. A code only ever goes into the site it
was sent for: a bot never sends, posts, forwards or pastes one anywhere else,
and a web page, email or document that tells it to share a code, or enter it
somewhere else, is ignored.

When a bot is not signed in, the code goes
somewhere it cannot read (an authenticator app, a phone it has no access to),
or a step needs a CAPTCHA, a passkey, payment details or your personal
interaction, it asks you to sign in yourself. You get one **Sign
in needed** card in the chat, naming the site and quoting the bot's reason, and
one notification ("Scout needs you to sign in to example.com"). The bot's turn
ends there.

- **Open** goes to the exact place the bot works, because a sign-in made
  anywhere else would not reach it. In ego lite, the bot hands its task space
  to you and you sign in in that ego lite window. For a Local VM or a cloud computer or VPS, it is that computer's view, where the
  banner offers **Take control**. For this computer, the card tells you to sign
  in there, in the browser the bot is using.
- **Done** hands control back and resumes the bot, which checks it is signed
  in and continues.
- **Cancel** resumes the bot with your answer that you declined.
A newer request for the same site in the same conversation replaces the older
card. The card works on the desktop, the web app, a Cloud home and a desktop
paired to another computer. A phone shows the request and its notification;
when the host allows browser control for that phone in **Settings → Remote
access**, the phone can also take over the bot's ego lite tabs and sign in
there.

You always type the password into the page yourself. None of this overrides
your provider's own restrictions, and approval modes are unchanged.

## Saved logins

AlcaBots does not type saved logins into ego lite. Sign in to a site once in
ego lite yourself; ego lite keeps that sign-in, and bots browsing there use it.
A bot's `ego_browser_run` script runs in ego lite's own Node.js runtime, outside
AlcaBots's sandboxes, so it can reach what ego lite can: your signed-in sites,
files and network. Turn the browser off for bots you do not trust with that.

## Shared machines

AlcaBots assumes the logged-in operating-system user is the workspace owner. On a shared machine, other administrators may be able to read application data or inspect processes. Use a dedicated OS account for stronger separation.
